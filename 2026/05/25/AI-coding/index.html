AI Coding

一些概念

Tool Use

MCP

COT

思维链

Agent

agent循环的本质：在上下文里面不断地追加思考和工具的结果

workflow

workflow与Agent的区别在于：agent是自己决定下一步要干什么，而workflow是提前确定了流程，只是按照顺序一步一步执行

具体来说：在workflow里面，LLM只负责某些特定步骤的处理，不负责决定流程的走向；而Agent则是模型自己决定下一步要做什么

Skills

可复用的工作流程，将常见任务的工作流程沉淀为skill

YAML：YAML Ain‘t Markup Language：YAML不是标记语言的递归缩写。只靠缩进分级，在md文件里面，yaml的部分由两行三个虚线包裹起来，称为前置元数据，给文章提供结构化的背景信息。同时在md转为html页面时，yaml部分也规定了如何渲染，如何分类，网页的关键词和描述等信息

skill的文件树：

其中SKILL.md为核心部分，yaml部分告诉agent什么时候该使用此skill，正文是具体的操作指南

scripts目录下是预写好的python脚本，通过读第一个md文件，agent知道在做不同操作的时候需要调用scripts下的哪些脚本

渐进式披露：启动时只告诉模型每个 Skill 的名字和一句话简介，等模型发现当前任务和某个 Skill 相关后，再加载更多的内容。防止所有skills全部放入上下文占据上下文窗口

围绕LLM的工程体系

Claude、Cursor等都是Agent层面的工具，即使使用相同的模型，编程效果也会有所差别，因为Agent的工程实现不一样，也就是组织上下文信息的方法不一样

SSE

server-sent events，服务器发送事件，是服务端主动向客户端持续推送数据的HTTP技术

注意：

  • 部署SSE服务时，注意开发服务器压缩和中间层数据缓冲，一旦出现这种情况，流式又会变成同步。解决方法，可以看response的响应头

  • 后端需要主动添加响应头，即使web框架会自动设置，为了兼并下游

CDN

content delivery network，内容分发网络。把网站的静态资源提前缓存到离用户更近的服务器上，让用户访问更快、更稳定。资源会被缓存到CDN上，这样就不用每次请求都需要去源服务器上拿，速度更快

CDN一般会储存图片、前端资源（js、css）、字体文件、音视频、安装包等等

Nginx

  • 高性能Web服务器：负责将写好的文件返回用户，比如用户访问某某网站，nginx就把对应网站下的静态文件返回

  • 反向代理：比如后端跑在私有地址不希望用户直接访问，而是希望用户访问另一个网址，此时就可以让nginx接受请求并转发到自己的地址

SDK

Software Development Kit，软件开发工具包，对底层接口封装，便于使用

接口调用

主流的API接口格式分为openai的chat completios格式和Anthropic的Messages接口格式

request中使用user标记用户说的话，response中使用assistant标记是模型的回答，choice本身是个数组，但默认只返回一条，因此使用下标0取第一个元素再取message再取content即可。注意会有一个字段finish_reason标记模型停止原因（感觉可以用下

每次API调用都是独立的，因此如果想要让模型记住之前的对话，必须将完整的对话历史全部放入调用API时的message字段。一轮对话就是一条user信息加一条assistant信息，最后一个user则是当前的提问。

ChatGPT之所以能够实现记住用户的上下文，就是其客户端帮忙维护了这个message数组。

每次调用API，request的message数组会越来越大，放入从开始到目前的所有用户和模型的回答。注意response的message一直就只有一个元素，也就是模型的回答。

返回的prompt_tokens是发送的message被拆成了多少token，也就是输入的消耗，返回的completion_tokens是模型生成的回答包含多少token，也就是输出消耗。

根据以上原理，对话历史越长，messages数组越长，prompt_tokens就越大，费用越高

除此之外，还有缓存命中token：例如messages前半部分都一样，只有最后的新消息不同。这是模型服务商在第一次计算完毕后就存入缓存中，后续请求如果前缀和缓存里面一致就会直接复用。不过缓存触发有一定条件（例如长度）还存在过期时间，字段名不同model不同

不是所有服务商都自动缓存，Claude模型就需要调用方主动标记缓存断点

从messages的角度来说，agent的核心就是管理好message数组，使模型在有限的上下文中尽可能聪明的工作

Agent入门

工具调用

  • 工具描述：定义工具，会传参给模型
  • 工具执行：自己使用，定义工具对应的真实实现
  • 结果回填：从模型的reply里面获得参数，执行工具，将工具结果回填到messages里面再进行调用

自主循环执行多个步骤

可复习服务器上记录的代码，其实agent的核心真的简单，关键在于围绕上下文等的工程化

流式传输

使用AI工具时答案逐字显示——底层获取数据就是逐字获得的，称为流式传输

目的：

  • 用户体验更好：如果不使用流式传输，等待模型生成完全部内容才显示，用户体验很差，不如流式传输可以边看答案边等；且用户发现答案错误的时候可以直接停止模型输出
  • 防止超时连接断开：防止HTTP连接在一定时间内没有收到数据断开连接

在调用接口的时候，设置”stream”=true开启流式传输，返回的信息中本来是message的地方变成了delta，把delta里面不同字段的内容拼接起来就是完整的message的各个字段的内容

简单实现看d05服务器上的代码

注意是markdown代码块渲染的时候需要处理一些特殊情况，例如代码````未闭合可以在检查到数量为奇数的时候先进行闭合

所以在一些AI使用页面里面发现代码未被渲染可能是没有处理这个问题。、

RAG：通过检索知识来增强回答

embedding

精确字符串匹配算法无法处理语义相似的文本，必须使用embedding将文本嵌入，使得语义相近的文本在向量空间上的距离也接近

sentence-transformer：专门加载和运行embedding模型的库；modelscope：阿里开源模型库

  • 切块：在进行embedding之前，要对需要加工的文档进行切块，不切块导致的后果：无法输入编码器，而且放入上下文中非常浪费token，且不一定文档里面所有的信息都会被用到
  • 代码看d05服务器上的代码
  • 相似度计算：当数据量太大时，使用numpy暴力计算余弦相似度速度非常慢，需要使用专门的近似最近邻索引
  • 文档更新的时候编码库应当支持增加删除操作
  • 文档元数据和编码的对应关系不可以仅靠下标维护
  • 所以需要引入向量数据库——chroma、LlamaIndex、Pinecone

RAG接入chatbot

核心逻辑是：用户每提出一个问题，就去做一次RAG检索，检索得到的文档加到system_prompt中，然后模型进行回答

embedding的原理

embedding模型使用大量的句子对训练，句子意思可以相近也可以不相关，然后使得相近句子的向量距离变近，不相近的句子向量距离变远。称为对比学习

数据如何分块

  • 不同格式的文件首先使用工具抽出纯文本

  • 长文本切成一个个的文本块叫做分块，做这件事的代码组件称为splitter切分器

  • 不能按照固定长度来切分，切分不能破坏语义完整性

  • recursive splitter：按照优先级切文本，先尝试按照段落切，如果太长在按照句号切，再按逗号切，最后才是字符切，尽可能保证每个chunk的语义完整性

  • chunk的长度不能太大，太大导致检索粒度很粗，浪费token，且编码的语义会不够精确；太小会导致一个chunk的信息不完整。chunk长度大小的经验值在200-500字之间

  • 相邻chunk要留出部分重叠，常见10-20%的重叠率，保留边界处的上下文

  • 表格中的信息需要整体处理，文档结构的标题可以作为元数据参与检索。

  • 可以看到chunk策略的好坏决定了RAG效果的好坏，现在通常使用已经做了工程优化的专门的splitter

RAG的使用场景

文档稳定不经常修改，规模较大、需要可追溯的引用、自然语言为主，单独通过关键词匹配不准确的文档检索场景

  • 企业知识库问答
  • 客服与工单系统
  • 法律和合规检索
  • 科研问答

所以code agent不会使用RAG，因为code的改动频率非常高，每次修改都需要充分划分chunk，且代码语义和自然语言不同，code里面对函数名、变量名等都为精确匹配，不需要语义相似。直接使用grep匹配字符串，同时grep也不需要像RAG一样上传代码计算向量，安全性和隐私性更高

长上下文模型无法取代RAG：

  • Lost in the Middle：模型对上下文开头和结尾的印象最深，中间的内容容易被一扫而过
  • 知识库直接放入上下文导致成本和延迟都非常高
